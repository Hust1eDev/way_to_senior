# OOP-03. Композиция

Статус: запланировано. Начинать после принятия OOP-02.

## Контекст

При регистрации новой заявки сервис должен сохранить ее и отправить уведомление. Правила состояния заявки уже существуют.

## Задание

Самостоятельно спроектируй взаимодействие сервиса регистрации, хранилища и отправителя уведомлений.

Требования:

- Сервис получает хранилище и отправителя извне при создании.
- Правила допустимого состояния заявки сохраняются в модели заявки.
- Сервис сначала сохраняет заявку, затем передает ее отправителю для уведомления.
- В первой версии хранилище работает в памяти, отправитель только записывает факт отправки в памяти.
- Можно получить сохраненную заявку по идентификатору. Отсутствующая заявка и повторное сохранение идентификатора вызывают явно описанные тобой исключения.
- При ошибке сохранения уведомление не отправляется, ошибка передается вызывающему коду.
- При ошибке уведомления сохраненная заявка остается в хранилище, ошибка передается вызывающему коду.
- Сервис не наследуется от хранилища или отправителя.
- Тесты проверяют успешную регистрацию, чтение, дубликат, отсутствие заявки и оба сценария ошибки.

Граница задачи: без БД, сети, asyncio, транзакций и повторных попыток. Частичный успех здесь задан явно; проблемы надежной доставки обсудим на review.
