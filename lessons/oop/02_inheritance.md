# OOP-02. Наследование

Статус: запланировано. Начинать после принятия OOP-01.

## Контекст

В сервисе появились инциденты. Инцидент остается заявкой: его можно прочитать, прокомментировать и закрыть по тем же правилам. Дополнительно у него есть уровень серьезности.

## Задание

- Спроектируй специализированный тип IncidentTicket на основе Ticket.
- Допустимые уровни: low, medium, high. Другие значения вызывают ValueError.
- Сохрани поведение обычной заявки, включая повторное закрытие и запрет комментариев после закрытия.
- Покажи один клиентский сценарий, который работает и с обычной заявкой, и с инцидентом через общий интерфейс.
- Не добавляй клиенту проверок конкретного типа для выбора поведения.
- Напиши тесты на специализацию и совместимость с поведением базового типа.

Повторное использование принятого кода и его переработку выполняешь самостоятельно.

## Вопросы для review

- Какие обещания дает базовая заявка?
- Может ли клиент безопасно получить инцидент вместо обычной заявки?
- Оправдывает ли одно дополнительное поле отдельный подкласс в реальном проекте?
- Как могла бы выглядеть альтернатива без наследования? Объясни словами, вторую реализацию писать не нужно.

Наследование здесь является учебным ограничением. В архитектурном обсуждении нужно оценить и его цену.
